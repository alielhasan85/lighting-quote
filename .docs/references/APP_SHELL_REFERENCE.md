# App Shell Reference

> **Status:** Built · **TODO:** — · **Related:** [AUTH_REFERENCE.md](AUTH_REFERENCE.md)

How a signed-in user reaches their workspace, and the sidebar shell around every workspace page.

## Quick Reference

```
app/page.tsx                           /: reads the caller and membership, redirects by landingPath. Renders nothing
app/layout.tsx                         Root metadata: the title template "%s · lighting-quote"
app/(auth)/welcome/page.tsx            /welcome: requireSignedInPage; a membership → /; otherwise the form
app/(auth)/welcome/welcome-client.tsx  The form: calls createWorkspace, then router.replace. A link to sign out
app/(app)/w/[workspaceId]/layout.tsx   Guard (DATA_READ) → getWorkspaceName, getCallerProfile, sidebar_state cookie → AppShell
app/(app)/w/[workspaceId]/page.tsx     Home: guard (DATA_READ) → ModuleTabs and an empty state
components/app-shell/AppShell.tsx      SidebarProvider + AppSidebar + SidebarInset, with a header holding SidebarTrigger
components/app-shell/AppSidebar.tsx    Workspace name, modules with icons, caller's name and email, sign-out. A module link closes the phone sheet
components/app-shell/ModuleTabs.tsx    Link tabs from { label, href }[], active by activeHref
lib/workspace/landing.ts               landingPath, WELCOME_PATH. Pure
lib/workspace/modules.ts               MODULES, moduleNav, isActivePath, activeHref. Pure
lib/actions/workspace.actions.ts       createWorkspace
lib/queries/workspace.queries.ts       getWorkspaceName

components/ui/sidebar.tsx              Generated by shadcn. Writes the sidebar_state cookie; Ctrl+B toggles
```

**Key concepts**

- **One workspace per account,** enforced in `createWorkspace`. There is no workspace switcher.
- **`landingPath` is the one rule** for where `/` sends someone.
- **A module has a route or it's disabled.** `segment: null` in `MODULES` means no `href`, and the sidebar renders a
  disabled button, not a link.
- **Runtime data is read inside `<Suspense>`** (`cacheComponents` is on): params, the session and cookies. A read outside
  it fails only in `next dev` or `next build`, not in typecheck or lint.

## Flow

```
Sign-in → /   Landing: getCaller → getLandingMembership → landingPath → redirect
                nobody                         /login
                suspended account              /forbidden
                no membership                  /welcome
                only a suspended membership    /forbidden
                active membership              /w/<id>

/welcome      WelcomeClient → createWorkspace({ name })                        createUserAction
                └─► $transaction: lock the User row → count memberships → create Workspace + OWNER Membership
                ok → /w/<id> · WORKSPACE_EXISTS → / · UNAUTHENTICATED → /login, back to /welcome
                other codes and a failed request show as a message

/w/<id>       layout: requireWorkspacePermissionPage(DATA_READ) → read the name → AppShell
              page:   requireWorkspacePermissionPage(DATA_READ) → render
```

## Rules

- `createWorkspace` uses `createUserAction`: signed-in and active, with no workspace yet, so no `Permission` applies.
  `userId` comes from the session and `role` is hardcoded `OWNER`.
- `createWorkspace`'s count includes suspended memberships, so a suspended member can't make a new workspace to get back
  in. It runs after the row lock, so a double submit sees the first workspace.
- The workspace layout and every page under it guard separately: the layout because it reads workspace data, the page
  because a layout doesn't re-run on navigation.
- `getWorkspaceName` runs only after the guard. A non-member and a missing workspace both get `/forbidden`, so a URL
  can't reveal which ids exist.
- An unbuilt module has no route. `/w/<id>/projects` is a 404 until its row builds it.
- Sign-out links to `/api/auth/signout` with `prefetch={false}`: it's a route handler, not a page.

## Common tasks

### Enable a module

1. Build its route at `app/(app)/w/[workspaceId]/<segment>/page.tsx`, with its own guard.
2. Set `segment: '<segment>'` on its entry in `MODULES`. `moduleNav` then gives it an `href`.

### Add a module to the sidebar

1. Add an entry to `MODULES` in sidebar order.
2. Add its icon to `ICONS` in `AppSidebar.tsx`. The type-check fails until it has one.

### Add tabs to a module

1. Render `<ModuleTabs tabs={[{ label, href }, ...]} />` from the page. Each tab is its own route, so each page guards.

## Decisions

| Decision | Why |
|---|---|
| One workspace per account, by a row lock and a count, not a unique constraint | `Membership` allows several per user on purpose: invites will need it. The limit is a rule of today's product, so it lives in the action |
| `/welcome` sits in `(auth)`, not `(app)` | It uses the centered layout and has no workspace to guard on |
| A signed-out visitor at `/` goes to `/login` | There is no marketing page |
| `/welcome` links to sign-out | `/login` sends a signed-in caller straight back, so someone on the wrong account would otherwise have to spend that account's one workspace |
| The Home page shows tabs with a single Overview tab | Later modules reuse `ModuleTabs`, so it's built and walked now |
| `ModuleTabs` drops `aria-controls` | Each tab is a link to its own page, so there is no panel to point at |
| The sidebar collapses to icons, not off-canvas | Modules stay one click away while an engineer works through a long list |
| Platform admins with no workspace go to `/welcome` | Admins don't pass workspace guards, so they're treated like anyone else |

## Known issues

- The row lock is proven by a mocked test to run first, not under a real double submit. The disabled button covers
  ordinary double-clicks, and the worst outcome of a miss is one extra empty workspace.
- `ModuleTabs` hasn't been walked by keyboard with two or more tabs: see LATER.md.
